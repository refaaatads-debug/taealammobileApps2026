ابدأ المرحلة التالية من مشروع أجيال المعرفة فقط، والتزم حرفياً بالقواعد التالية:

⚠️ قاعدة المشروع الأساسية — ممنوع تجاوزها:
- لا تعدّل قاعدة البيانات Production بأي شكل.
- لا تعدّل Schema أو Tables أو Columns.
- لا تعدّل RLS.
- لا تعدّل RPC.
- لا تعدّل Functions أو Triggers.
- لا تعدّل Supabase Auth أو Storage أو Realtime.
- لا تعدّل VPS.
- لا تعدّل الكود الرئيسي للمنصة الأصلية.
- لا تنفذ أي عملية مالية أو دفع أو خصم أو استرجاع.
- لا تنفذ حجزاً أو جلسة حقيقية على Production.
- لا تستخدم بيانات شخصية أو كلمات مرور أو Tokens حقيقية.
- أي نقطة تحتاج تغييراً في Production يجب تصنيفها BLOCKED / UNVERIFIED وعدم اختراع حل بديل لها.
- جميع الإصلاحات المسموح بها تكون داخل تطبيق الهاتف والـAPI الخاص بالتطبيق فقط، ما لم يكن الإصلاح يتطلب تغييراً في Production.

الهدف:
إكمال تدقيق ومطابقة تطبيق الهاتف مع المنصة الأصلية حتى نصل إلى 100% Parity، مرحلة بعد مرحلة، بناءً على:
1. المخططات الهندسية المرفقة.
2. كود المنصة الأصلي.
3. كود API.
4. قاعدة البيانات كما هي موثقة ومقروءة.
5. التقارير السابقة للمراحل المنجزة.

لا تعتمد على التخمين أو المنطق العام إذا لم يكن مدعوماً بالمخططات أو الكود.

المرحلة الحالية
━━━━━━━━━━━━━━━━━━━━

ابدأ أولاً بقراءة ملف مواصفة المرحلة الحالية والمخططات الهندسية المرفقة بالكامل.

قبل تعديل أي كود:

1. حدد نطاق المرحلة بدقة.
2. اقرأ المسارات المقابلة في المنصة الأصلية.
3. اقرأ المسارات المقابلة في API.
4. اقرأ المسارات المقابلة في تطبيق الهاتف.
5. قارن:
   - Events
   - States
   - API calls
   - Database reads
   - Database writes
   - Permissions
   - Roles
   - Navigation
   - Validation
   - Error handling
   - Loading states
   - Empty states
   - Notifications
   - Realtime
   - Idempotency
   - Financial effects إن وجدت
6. لا تعتبر وجود واجهة مشابهة دليلاً على تطابق المنطق.
7. لا تعتبر نجاح Build دليلاً على تطابق الوظيفة.
8. لا تعتبر نجاح API 200 دليلاً على صحة البيانات أو الـbusiness logic.
9. لا تنشئ Mock Data لتعويض وظيفة غير موجودة.
10. لا تخترع RPC أو Trigger أو Database logic غير مثبت في المصدر.

التقرير الإجباري قبل الإصلاح
━━━━━━━━━━━━━━━━━━━━

أنشئ تقريراً باسم مناسب للمرحلة، مثلاً:

[STAGE_NAME]_PARITY_REPORT.md

ويجب أن يحتوي على جدول لكل وظيفة:

| الوظيفة | المنصة الأصلية | تطبيق الهاتف | API | الحالة | الخطورة | الدليل | المطلوب |
|---|---|---|---|---|---|---|---|

استخدم الحالات فقط:

MATCHED
PARTIAL
MISMATCH
UNVERIFIED
BLOCKED

وفرّق بوضوح بين:

- مخالفة مؤكدة من الكود.
- فجوة جزئية.
- شيء غير قابل للإثبات دون Production.
- شيء يحتاج تغييراً ممنوعاً حالياً.

لا تبدأ الإصلاح قبل تثبيت تقرير ما قبل الإصلاح.

التحقق بعد الإصلاح
━━━━━━━━━━━━━━━━━━━━

بعد الانتهاء من الإصلاحات المسموحة فقط:

شغّل:

- Mobile TypeScript
- API TypeScript
- API build
- Android bundle
- iOS bundle
- Expo startup
- OpenAPI generation إذا كان متأثراً
- git diff --check

ثم تحقق من:

- API health
- Authentication behavior
- Authorization
- 401/403 عند الحاجة
- عدم وجود JavaScript Runtime errors
- عدم وجود Crash
- عدم وجود Navigation loop
- عدم وجود Loading state لا نهائي
- عدم وجود Mock/Fallback يخالف المنصة

لا تعتبر التحذيرات البيئية مثل:

libglib-2.0.so.0

فشلاً وظيفياً إذا ثبت أنها خاصة ببيئة التطوير ولا تمنع التطبيق.

بعد التحقق
━━━━━━━━━━━━━━━━━━━━

حدّث تقرير المرحلة نفسه وأضف:

### BEFORE
الفروقات قبل الإصلاح.

### FIXED
كل ما تم إصلاحه فعلياً.

### REMAINING
كل ما بقي.

### BLOCKED
كل ما يحتاج Production.

### UNVERIFIED
كل ما لم يمكن إثباته بدون حساب/جهاز/Production.

### VERIFICATION
نتائج TypeScript / Build / Expo / API / Security.

### PRODUCTION SAFETY
اكتب صراحة:

Database changed: NO
Schema changed: NO
RLS changed: NO
RPC changed: NO
Functions changed: NO
Triggers changed: NO
Auth settings changed: NO
Storage changed: NO
Realtime changed: NO
VPS changed: NO
Main platform code changed: NO
Production writes: NO

قاعدة الوصول إلى 100%
━━━━━━━━━━━━━━━━━━━━

لا تقل إن التطبيق أصبح 100% إلا إذا كانت كل الوظائف مثبتة فعلياً.

أي بند غير مثبت يجب أن يبقى:

UNVERIFIED

وأي بند يتطلب تعديل Production يجب أن يبقى:

BLOCKED

ولا تعتبر Build ناجحاً = Parity ناجحة.

بعد انتهاء المرحلة الحالية:

1. أعطني تقريراً مختصراً بما تم.
2. أعطني قائمة دقيقة بما بقي.
3. أعطني المرحلة التالية المقترحة.
4. لا تبدأ المرحلة التالية تلقائياً.
5. توقف وانتظر موافقتي.

الأهم:
أريد إصلاحاً حقيقياً مبنياً على المخططات والكود، وليس ترقيعات شكلية أو حلولاً تخمينية.
