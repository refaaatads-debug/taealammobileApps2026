==================================================

→ المرحلة
→ مدة الجلسة
→ اليوم
→ الوقت
→ إنشاء طلب الحجز

يجب التأكد من:

- الطالب مصادق.
- الدور student.
- المعلم موجود.
- المعلم معتمد.

- لا يتم إرسال teaching_stage إذا لم يكن جزءًا من العقد الأصلي.
- لا يتم اختراع teacher matching logic.

ثم تحقق من نتيجة قاعدة البيانات فعليًا.

==================================================
5) النظام الثاني: الحجز المفتوح حسب المادة
==================================================

هذا جزء أساسي ولا يجوز تجاهله.

الطالب لا يختار معلمًا.

يختار فقط مثلًا:

- المادة
- المرحلة
- مدة الجلسة
- اليوم
- الوقت
- وأي شروط أخرى موجودة أصلًا في المنصة.

ثم:

الطالب
→ booking request
→ بدون teacher_id إذا كان هذا هو عقد المنصة
→ النظام يبحث عن جميع المعلمين المؤهلين
→ المعلمون الذين تنطبق عليهم الشروط
→ المادة
→ الاعتماد
→ availability
→ المرحلة/الشروط التي تثبتها المنصة
→ يتم إرسال الطلب للمعلمين المؤهلين
→ أول معلم يقبل
→ يصبح هو صاحب الجلسة/الحجز
→ باقي المعلمين لا يستطيعون قبول نفس الطلب.

لا تحول الحجز المفتوح إلى حجز معلم عشوائي واحد.

لا تختار معلمًا من الهاتف.

لا تستخدم أول معلم في Array.

لا تستخدم Random محلي.

لا تستخدم fallback.

يجب مطابقة First Accept Wins مع المنصة الأصلية.

==================================================
9) FIRST ACCEPT WINS
==================================================

هذا اختبار إلزامي.

استخدم معلمين مؤهلين لنفس الطلب المفتوح.

حاول:

Teacher A → Accept
Teacher B → Accept

في نفس الوقت أو بفارق زمني ضئيل جدًا.

يجب أن يكون:

ONE ACCEPTED

والباقي:

REJECTED / ALREADY_ACCEPTED / CONFLICT

حسب سلوك المنصة الحقيقي.

لا يكفي اختبار UI.

يجب فحص Database بعد العملية.

إذا كان النظام يسمح بقبولين:
صنفها:

CRITICAL / BLOCKED

ولا تصلحها من Mobile فقط.

==================================================
10) RACE CONDITIONS
==================================================

اختبر على الأقل:

A) معلمان يقبلان نفس الطلب.
B) طلبان لنفس الموعد.
C) إنشاء حجزين لنفس الطالب في نفس الوقت.
D) آخر دقائق subscription مع طلبين متزامنين.
E) نفس request يتم إرساله مرتين.
F) retry بعد timeout.
G) double tap على زر الحجز.

تحقق من:

- duplicate bookings
- duplicate charges
- duplicate notifications
- duplicate sessions
- negative remaining_minutes
- inconsistent statuses

يجب تحديد هل الحماية:

Mobile
API
RPC
Database constraint
Transaction
Lock

إذا كانت Database/RPC مطلوبة:
سجلها BLOCKED بدل عمل workaround في Mobile.
