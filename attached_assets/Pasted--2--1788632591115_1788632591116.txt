نبدأ الآن المرحلة 2 فقط من مشروع مطابقة تطبيق الهاتف مع المنصة الأصلية.

المطلوب:
تدقيق وتنفيذ مطابقة كاملة لوحدة:

STUDENT DASHBOARD / HOME

ممنوع الانتقال إلى الاشتراكات أو الحجز أو الجلسات في هذه المرحلة إلا إذا كان ذلك ضرورياً لفهم بيانات لوحة الطالب، ودون تعديلها.

قواعد إلزامية:

1. المنصة الأصلية وProduction هما مصدر الحقيقة.
2. التطبيق مشروع مستقل.
3. ممنوع منعاً باتاً تعديل:
   - Production Database
   - Schema
   - Tables
   - Columns
   - RLS
   - RPC
   - Functions
   - Triggers
   - Auth
   - OAuth
   - Storage Policies
   - Realtime configuration
   - VPS
   - Nginx
   - Kong
   - كود المنصة الأصلية.
4. لا Migration.
5. لا Deploy إلى Production.
6. لا إنشاء جداول أو بيانات بديلة داخل التطبيق.
7. لا تخمين لأي سلوك غير مثبت.
8. أي نقطة لا يمكن إثباتها من كود المنصة أو المخططات أو Production read-only يجب تصنيفها UNVERIFIED وعدم اختراع حل لها.
9. أي تعديل يتم داخل تطبيق الهاتف/API الخاص بالتطبيق فقط.
10. لا تستخدم Password أو Access Token أو Refresh Token من المحادثة.
11. لا تنفذ أي عملية مالية أو Booking أو RPC كتابة على Production.
12. لا تعتبر نجاح TypeScript أو Build دليلاً على تطابق الوظيفة.

نفذ العمل بهذا الترتيب:

أولاً — استخراج الحقيقة من المنصة

راجع المخططات الهندسية والكود المتاح للمنصة الأصلية، وحدد بالتفصيل:

- الصفحة الرئيسية للطالب.
- كل البيانات التي تظهر فيها.
- مصدر كل Data.
- الجداول/views/RPCs المستخدمة.
- العلاقات بين البيانات.
- شروط RLS أو الصلاحيات إن كانت قابلة للإثبات.
- ترتيب البيانات.
- حالات loading.
- حالات empty.
- حالات error.
- حالات الحساب غير المكتمل.
- الاشتراك الحالي إن ظهر.
- الباقة الحالية إن ظهرت.
- الدقائق/الرصيد إن ظهر.
- الحجوزات القادمة.
- الجلسات الحالية أو السابقة إن ظهرت.
- المعلمين المقترحين إن ظهروا.
- الإشعارات.
- الرسائل غير المقروءة.
- الواجبات أو المهام إن ظهرت.
- أي badges أو counters.
- أي redirect أو guard مرتبط بلوحة الطالب.

ثانياً — مطابقة التطبيق الحالي

راجع الكود الحالي لتطبيق الهاتف، خصوصاً:

- app/_layout.tsx
- auth.tsx
- شاشة Home/Index الخاصة بالطالب
- lib/api-client
- lib/api-spec
- routes المرتبطة بالطالب
- أي hooks أو stores أو context
- أي API endpoint يستخدمه Dashboard.

اعمل جدولاً:

FEATURE
PLATFORM SOURCE
MOBILE SOURCE
STATUS
EVIDENCE
RISK
REQUIRED FIX

واستخدم فقط:

MATCHED
PARTIAL
MISMATCH
UNVERIFIED
NOT_APPLICABLE

ثالثاً — ابحث عن الفروقات الفعلية

ركز خصوصاً على:

- اختلاف مصدر البيانات.
- اختلاف user_id.
- اختلاف role.
- اختلاف subscription selection.
- اختلاف حالات booking.
- اختلاف عداد الإشعارات.
- اختلاف الرسائل.
- اختلاف الدقائق.
- اختلاف ترتيب العناصر.
- اختلاف empty states.
- اختلاف loading.
- اختلاف error handling.
- اختلاف صلاحيات الطالب.
- API يستخدم بيانات محلية بدلاً من Supabase.
- API endpoint يعيد بيانات أكثر أو أقل مما تعيده المنصة.
- أي fallback قد يؤدي إلى بيانات غير مطابقة.

رابعاً — أصلح فقط الفروقات المؤكدة

إذا وجدت MISMATCH أو PARTIAL مثبتاً:

- أصلحه داخل تطبيق الهاتف/API فقط.
- استخدم نفس الجداول والـviews والـRPCs الموجودة أصلاً.
- لا تنشئ بديلاً.
- لا تغير Production.
- لا تغير RLS لمحاولة جعل التطبيق يعمل.
- لا تضف بيانات افتراضية.
- لا تغير منطق المنصة الأصلية.

إذا كان الإصلاح يحتاج تعديل Production:
توقف فوراً ولا تنفذ الإصلاح، وصنفه:

BLOCKED — REQUIRES PRODUCTION CHANGE

خامساً — الاختبارات

بعد الإصلاح نفذ:

- Mobile TypeScript
- API TypeScript
- API build
- Expo startup
- Android bundle
- iOS bundle
- فحص routes
- فحص API responses بدون أي بيانات شخصية في التقرير
- فحص أن التطبيق لا يستخدم local fallback مخالف للمنصة.

إذا كانت هناك اختبارات قراءة فقط ممكنة من Production، نفذها بدون أي كتابة.

سادساً — لا تدّعِ 100%

لا تقل إن المرحلة مكتملة 100% إلا إذا كان ذلك مثبتاً.

في النهاية أعطني تقريراً بهذا الشكل:

1. STATUS
2. ما تم إثباته
3. MATCHED
4. PARTIAL
5. MISMATCH
6. UNVERIFIED
7. BLOCKED
8. الملفات التي تم تعديلها
9. ما تم اختباره
10. ما لم يتم اختباره
11. هل تم لمس Production؟ 
12. هل تم تعديل Database/RLS/RPC/Auth/VPS؟
13. ما هي الخطوة التالية المقترحة فقط.
