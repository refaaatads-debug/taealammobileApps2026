أريد منك إجراء تشخيص دقيق لمشكلة الاتصال بين التطبيق وSupabase، وليس مجرد تغيير رسالة الخطأ أو عمل workaround.

مهم جدًا:
- لا تحذف أو تعيد إنشاء Supabase Integration.
- لا تغيّر أو تستبدل أي Secrets أو مفاتيح.
- لا تعدّل RLS أو Authentication أو قاعدة البيانات.
- لا تغيّر كود شاشة الحماية قبل تحديد سبب المشكلة.
- لا تعتبر المشكلة محلولة لمجرد إخفاء الخطأ.
- أريد معرفة السبب الجذري Root Cause أولًا.

المشكلة:
التطبيق كان يعمل بشكل طبيعي سابقًا، ثم أصبح عند محاولة الدخول يظهر:
"تعذر التحقق من الحساب
لم نتمكن من قراءة ملفك وصلاحياتك من المنصة."

المراجعة السابقة أظهرت أن هناك طلبًا ينتظر حوالي 13.8 ثانية ثم يتم إلغاؤه، وظهر سابقًا 403 Forbidden عند محاولة الاتصال بـ Supabase.

تم فحص مشروع Supabase نفسه، وهو يعمل وتظهر فيه الجداول والـFunctions بشكل طبيعي.
كما تم فتح Supabase Logs & Analytics، وبعد محاولة تسجيل الدخول من التطبيق لم يظهر أي Request أو Log جديد.

هذا مهم جدًا:
إذا كانت محاولة تسجيل الدخول لا تظهر أصلًا في Supabase Logs، فأريد منك تحديد هل الطلب يفشل داخل Replit/API قبل أن يصل إلى Supabase.

نفّذ الآن فحصًا تشخيصيًا فقط:

1. افحص الكود المسؤول عن:
   - إنشاء Supabase client
   - الاتصال بـ Supabase
   - API/server routes
   - شاشة الحماية والتحقق من الحساب والصلاحيات
   - أي timeout أو AbortController أو retry logic.

2. افحص جميع متغيرات البيئة المستخدمة للاتصال بـ Supabase، لكن لا تعرض أي Secret أو Key في النتائج.
   تحقق فقط من:
   - هل المتغير موجود؟
   - هل اسمه صحيح؟
   - هل التطبيق يقرأه فعلًا؟
   - هل SUPABASE_URL يشير إلى المشروع الصحيح؟
   - هل هناك اختلاف بين متغيرات بيئة development/production؟
   - هل يوجد متغير قديم أو اسم متغير تغيّر؟

3. تتبع الطلب الفعلي من لحظة ضغط المستخدم على تسجيل الدخول حتى نقطة فشل التحقق.
   حدد:
   - أي endpoint يتم استدعاؤه؟
   - هل الطلب يصل إلى server/API؟
   - هل server يحاول الاتصال بـ Supabase؟
   - أين يظهر الـ403؟
   - هل الـ403 صادر من Supabase أم من Replit/Proxy/API آخر؟
   - هل هناك timeout قبل إرسال الطلب أصلًا؟

4. افحص Logs الخاصة بـ Replit/Server وقت تنفيذ الطلب.
   أضف logging تشخيصي مؤقت وآمن إذا كان ضروريًا، بشرط:
   - عدم طباعة أي Secrets أو Tokens أو Authorization headers.
   - تسجيل URL/endpoint بشكل آمن.
   - تسجيل HTTP status.
   - تسجيل مدة الطلب.
   - تسجيل اسم العملية التي فشلت.
   - تسجيل مصدر الخطأ الحقيقي.

5. اختبر الاتصال بـ Supabase من بيئة تشغيل التطبيق نفسها، وليس من متصفح المستخدم فقط.
   أريد معرفة:
   - هل DNS يعمل؟
   - هل HTTPS connection يعمل؟
   - هل Supabase URL يمكن الوصول إليه من Replit؟
   - هل الطلب يصل إلى Supabase؟
   - ما HTTP status الفعلي؟
   - وهل المشكلة Authentication أم Network أم Environment Variables أم Proxy؟

6. قارن الكود الحالي مع Git history / checkpoints / آخر نسخة كان التطبيق يعمل فيها، إذا كان ذلك متاحًا.
   ابحث تحديدًا عن أي تغيير حدث قبل ظهور المشكلة في:
   - Supabase client
   - API routes
   - environment variables
   - authentication
   - timeout
   - middleware
   - proxy
   - deployment configuration.

7. لا تقم بأي إصلاح نهائي الآن.
   أريد منك أولًا أن تعطيني تقريرًا واضحًا بهذا الشكل:

ROOT CAUSE:
[السبب المرجح بدليل]

REQUEST FLOW:
[من التطبيق → API → Supabase وما النقطة التي يتوقف عندها]

SUPABASE:
[هل وصل الطلب إلى Supabase أم لا؟ وما الدليل؟]

REPLIT:
[هل المشكلة داخل Replit/API؟ وما الدليل؟]

ENVIRONMENT:
[هل توجد مشكلة في Secrets/Environment Variables؟ بدون إظهار قيمها]

WHAT CHANGED:
[ما الذي تغيّر مقارنة بآخر نسخة تعمل، إن أمكن]

CONFIDENCE:
[نسبة ثقتك في التشخيص]

SAFE FIX:
[الإصلاح المقترح فقط، بدون تنفيذه]

ثم توقف وانتظر موافقتي قبل إجراء أي تعديل.
