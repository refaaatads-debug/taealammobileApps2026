أكيد. هذا **برومبت شامل ودقيق** لـ Replit Agent، ويجمع: حماية المنصة الأساسية، الرجوع للنسخة السليمة، تشخيص سبب المشكلة، منع تأثير التطبيق، ومطابقة التطبيق مع المنصة دون تغيير قاعدة البيانات.

انسخه بالكامل:

> ## 🚨 مهمة حرجة: حماية المنصة الأصلية وإصلاحها ثم استكمال التطبيق
>
> **الهدف النهائي:**
> أريد أن تكون **المنصة الأصلية والتطبيق مرتبطين بنفس المستخدم ونفس بيانات Production ونفس منطق الأعمال**، لكن **ممنوع تماماً أن يؤثر التطبيق على المنصة الأصلية أو يغيّر أي خاصية موجودة فيها**.
>
> ### أولاً — أوقف أي تغييرات خطرة
>
> * أوقف أي Deploy أو Migration أو تعديل مباشر على Production أثناء الفحص.
> * لا تنشئ أو تحذف أو تعدّل أي جدول في Supabase Production.
> * لا تعدّل RLS أو RPC أو Functions أو Triggers أو Policies.
> * لا تغيّر Google Client ID / Client Secret أو إعدادات OAuth إلا بعد إثبات أن تغييراً سابقاً تسبب بالمشكلة.
> * لا تستخدم بيانات تجريبية أو Mock Data بدلاً من بيانات Production.
> * لا تحذف أي مستخدم أو حجز أو اشتراك أو فاتورة أو معاملة.
>
> ---
>
> ## 1 — إعادة المنصة الأصلية إلى آخر حالة سليمة
>
> افحص GitHub وGit history وVPS وحدد:
>
> **آخر Commit / Backup كانت فيه المنصة الأصلية تعمل بشكل صحيح قبل تعديلات التطبيق.**
>
> قارن هذه النسخة مع Production الحالية، وحدد كل التغييرات المتعلقة بـ:
>
> * Authentication
> * Login / Signup
> * Google OAuth
> * Apple Login
> * Redirect URLs
> * Sessions
> * Cookies
> * Middleware
> * Roles / Permissions
> * API
> * Routes
> * Supabase
> * Environment Variables
> * Frontend
> * Backend
>
> لا تعمل Rollback عشوائياً.
>
> **حدد أولاً الملفات والتغييرات التي سببت المشكلة، ثم أعد فقط ما يلزم بأمان.**
>
> ---
>
> ## 2 — إصلاح تسجيل الدخول
>
> عالج بشكل كامل:
>
> * تسجيل الدخول بالبريد.
> * إنشاء حساب جديد.
> * تسجيل الخروج.
> * استمرار الجلسة.
> * استعادة الجلسة بعد إعادة تحميل الصفحة.
> * Google Login.
> * Apple Login إن كان موجوداً.
> * تحديد Role الصحيح للمستخدم.
> * إعادة المستخدم بعد تسجيل الدخول إلى **لوحة التحكم الصحيحة** وليس الصفحة الرئيسية.
>
> اختبر:
>
> **Signup → Login → Session → Role → Dashboard → Logout → Login Again**
>
> ---
>
> ## 3 — حماية خصائص المنصة الأصلية
>
> أنشئ مقارنة **Baseline / Regression** بين آخر نسخة سليمة والنسخة الحالية.
>
> تأكد أن **أي خاصية موجودة في المنصة الأصلية لم تتغير أو تتعطل**، خصوصاً:
>
> * لوحة الطالب.
> * لوحة المعلم.
> * لوحة الإدارة.
> * المعلمين.
> * المواد والمراحل.
> * التقييمات.
> * الأسعار.
> * التوفر والمواعيد.
> * نظام الحجز.
> * طلبات الحجز.
> * قبول ورفض المعلم.
> * إعادة الجدولة.
> * الإلغاء.
> * الباقات.
> * الاشتراكات.
> * الرصيد والدقائق.
> * الدفع.
> * الفواتير.
> * المحفظة.
> * الإشعارات.
> * المكالمات.
> * الجلسات.
> * التقارير.
> * جميع API.
> * جميع Routes.
> * جميع الصلاحيات.
>
> **ممنوع إصلاح تسجيل الدخول إذا كان الإصلاح سيؤدي إلى تغيير وظيفة أخرى.**
>
> ---
>
> ## 4 — افصل التطبيق عن المنصة وظيفياً
>
> التطبيق يجب أن يستخدم نفس Production ونفس حساب المستخدم، ولكن يجب ألا يغيّر كود التطبيق سلوك المنصة الأصلية.
>
> افحص وجود أي:
>
> * Shared Middleware
> * Shared Auth Logic
> * Shared Routes
> * Redirects
> * Environment Variables
> * API Changes
> * OAuth Changes
> * Database Writes
>
> يمكن للتطبيق **استهلاك الـAPI والمنطق الموجود**، لكن لا تعيد كتابة منطق المنصة الأصلي بطريقة مختلفة.
>
> إذا كان هناك منطق أصلي موجود بالفعل للحجز أو الاشتراكات أو الجلسات، **استخدمه كما هو**.
>
> ---
>
> ## 5 — مطابقة التطبيق مع المنصة الأصلية
>
> بعد استقرار المنصة الأصلية، أكمل التطبيق ليستخدم نفس:
>
> * Users
> * Profiles
> * Roles
> * Teachers
> * Subjects
> * Availability
> * Booking Requests
> * Bookings
> * Sessions
> * Subscriptions
> * Subscription Plans
> * Invoices
> * Payments
> * Wallet
> * Notifications
>
> **لا تنشئ جداول بديلة أو نسخاً ثانية من هذه البيانات.**
>
> المستخدم يجب أن يكون **مستخدماً واحداً** في المنصة والتطبيق، وليس حسابين منفصلين.
>
> ---
>
> ## 6 — نظام الحجز
>
> راجع المنصة الأصلية أولاً وافهم دورة الحجز الحقيقية، ثم طبقها في التطبيق **بنفس الترتيب والمنطق**:
>
> **اختيار المعلم → اختيار الموعد → التحقق من التوفر → التحقق من الباقة/الرصيد → إنشاء طلب الحجز → ظهور الطلب للمعلم → قبول/رفض → إنشاء الحجز المؤكد → الجلسة**
>
> لا تخترع دورة حجز جديدة إذا كانت المنصة الأصلية لديها دورة قائمة.
>
> استخدم الـRPC / API / Functions الأصلية الموجودة عند توفرها.
>
> تأكد أن المعلمين يظهرون في التطبيق بنفس شروط ظهورهم في المنصة.
>
> ---
>

>
> * عرض الباقات.
> * الاشتراك.
> * الاشتراك المجاني إن وجد.
> * الرصيد بالدقائق.
> * تاريخ البداية والنهاية.
> * الاشتراك النشط.
> * الاشتراكات السابقة.
> * الدفع.
> * الفواتير.
> * المعاملات.
> * خصم الدقائق.
> * إعادة الدقائق عند الإلغاء حسب منطق المنصة.
>
> **ممنوع إنشاء نظام اشتراكات جديد.**
>
> استخدم `subscription_plans` و`user_subscriptions` وباقي الجداول والمنطق الأصلي الموجود فعلياً.
>

> * انقطاع الاتصال.
> * التعويضات.

> * تحديث حالة الجلسة.
>
> لا تنشئ نظام مكالمات منفصلاً عن النظام الأصلي.
>

>
> ## 9 — التزامن والبيانات
>
> كل عملية في التطبيق يجب أن تعكس نتيجتها في المنصة، والعكس، باستخدام نفس Production.
>
> اختبر التزامن في:
>
> **الحجز / الاشتراك / الرصيد / الجلسات / الإشعارات / المدفوعات / حالة المعلم**
>
> امنع:
>
> * Duplicate Records
> * Double Booking
> * Double Deduction
> * Race Conditions
> * بيانات قديمة من Cache
> * Mock Data
> * بيانات محلية تخالف Production
>
> ---
>
> ## 10 — قاعدة مهمة جداً
>
> **لا تعدّل قاعدة البيانات لمجرد جعل التطبيق يعمل.**
>
> إذا وجدت أن التطبيق لا يتوافق مع قاعدة البيانات أو المنصة، **عدّل التطبيق والكود أولاً ليطابق النظام الموجود**.
>
> لا تنشئ Migration إلا إذا كان هناك احتياج حقيقي مثبت، وحتى في هذه الحالة **توقف واطلب موافقتي قبل تنفيذها على Production**.
>
> ---
>
> ## 11 — الاختبار النهائي
>
> بعد الإصلاح، نفذ Regression Test شامل:
>
> ### الطالب
>
> إنشاء حساب → تسجيل دخول → لوحة الطالب → رؤية المعلمين → اختيار معلم → اختيار موعد → حجز → ظهور الطلب → قبول المعلم → الحجز المؤكد → دخول الجلسة → إنهاء الجلسة → تحديث الرصيد.
>
> ### المعلم
>
> تسجيل دخول → لوحة المعلم → ظهور الطلب → قبول/رفض → ظهور الموعد → دخول الجلسة → إنهاء الجلسة → تحديث الحالة والأرباح.
>
> ### الاشتراك
>
> عرض الباقات → الاشتراك → تحديث الرصيد → استخدام الرصيد في الحجز → خصم صحيح → تحديث البيانات.
>
> ### Authentication
>
> Email Login → Google Login → Role → Dashboard → Logout → Login Again.
>
> ---
>
> ## 12 — معيار النجاح
>
> لا تعتبر المهمة مكتملة إلا إذا تحققت الشروط التالية:
>
> **المنصة الأصلية تعمل كما كانت قبل المشكلة.**
>
> **جميع خصائص المنصة الأصلية ما زالت تعمل بدون تغيير.**
>
> **التطبيق يستخدم نفس المستخدم ونفس Production.**
>
> **بيانات التطبيق والمنصة متطابقة ومتزامنة.**
>
> **الحجز يعمل بنفس منطق المنصة الأصلية.**
>
> **الباقات والاشتراكات والرصيد تعمل بنفس منطق المنصة.**
>
> **تسجيل الدخول يعيد المستخدم إلى لوحة التحكم الصحيحة.**
>
> **لا توجد تغييرات غير مصرح بها في قاعدة البيانات.**
>
> ---

>
> بعد الانتهاء أعطني تقريراً مختصراً جداً يحتوي على:
>
> **1. سبب المشكلة:**
> **2. التغييرات التي سببتها:**
> **3. النسخة السليمة التي تم الاعتماد عليها:**
> **4. ما تم إصلاحه:**
> **5. هل تغيرت أي خاصية من المنصة الأصلية؟ نعم/لا:**
> **6. هل تم تعديل Production Database؟ نعم/لا:**
> **7. نتيجة اختبار Login / Google / Booking / Subscription:**
> **8. ما المتبقي للوصول إلى تطابق 100%؟**
>
> **الأولوية القصوى: حماية المنصة الأصلية وبيانات Production. لا تقم بأي تغيير خطير أو غير قابل للعكس دون موافقتي الصريحة.**
