أنت تعمل كمهندس DevOps على VPS يعمل عليه Docker وSupabase. نفّذ المهمة بحذر وبأسلوب تشخيصي، ولا تحذف أي بيانات أو حاويات أو Volumes.

## المشكلة الحالية
- CPU Steal وصل سابقًا إلى 89.5%، ثم ظهر لاحقًا حوالي 51.9%.
- Load average مرتفع جدًا: 18.51 / 23.58 / 30.33.
- الخادم لديه حوالي 3124 عملية Zombie.
- Docker يعمل، لكن حاويات Supabase التالية تعيد التشغيل باستمرار:
  - supabase-pooler
  - supabase-auth
  - realtime-dev.supabase-realtime
- حاوية قاعدة البيانات ظهرت بحالة Exited، بينما بقية الخدمات تحاول الاتصال باسم supabase-db.
- سجلات الخدمات تشير إلى أن الاسم supabase-db لا يمكن حله أو أن قاعدة البيانات غير متاحة.

## الهدف
1. تحديد مجلد مشروع Supabase وملف Docker Compose الفعلي المستخدم.
2. معرفة سبب توقف حاوية قاعدة البيانات.
3. إعادة تشغيل قاعدة البيانات بأمان، ثم تشغيل الخدمات التابعة بالترتيب الصحيح.
4. إيقاف حلقة إعادة التشغيل التي تستهلك CPU وتمنع تكاثر عمليات Zombie.
5. التحقق من أن Supabase يعمل وأن المنافذ والخدمات الأساسية سليمة.
6. تقليل استهلاك CPU بعد الإصلاح.

## قواعد أمان إلزامية
- لا تنفذ reboot للخادم.
- لا تستخدم docker system prune.
- لا تحذف أي Container أو Volume أو Network.
- لا تستخدم docker compose down -v.
- لا تمسح ملفات PostgreSQL أو مجلدات البيانات.
- لا تغير كلمات المرور أو مفاتيح Supabase أو ملفات البيئة.
- لا تعيد تشغيل كل الخدمات دفعة واحدة.
- خذ نسخة من ملفات Compose وملفات البيئة قبل تعديلها، مع عدم طباعة الأسرار في المخرجات.
- قبل أي إصلاح قد يؤثر على البيانات، اعرض لي الأمر والسبب وانتظر موافقتي.

## خطوات التشخيص المطلوبة
نفّذ أولًا أوامر قراءة فقط:
- docker ps -a
- docker compose ls
- تحديد ملفات compose الخاصة بـ Supabase
- فحص حالة قاعدة البيانات وسجلاتها، مع آخر 100 سطر فقط
- فحص Volumes المرتبطة بقاعدة البيانات
- فحص المساحة: df -h و docker system df
- فحص العمليات: ps aux --sort=-%cpu | head -30
- عدّ عمليات Zombie وتحديد الـ parent process المسؤول عنها
- فحص آخر أخطاء النظام المتعلقة بالقرص أو الذاكرة أو Docker

لا تعرض أي قيمة من ملفات .env أو أي مفتاح أو كلمة مرور أو service_role.

## طريقة اتخاذ القرار
- إذا كانت حاوية PostgreSQL متوقفة بسبب امتلاء القرص، حدّد الملفات أو Logs الكبيرة فقط، ولا تحذف شيئًا قبل عرضها.
- إذا كانت متوقفة بسبب خطأ في البيانات، لا تشغّل إصلاحات PostgreSQL تلقائية ولا تستخدم fsck أو أوامر تهيئة.
- إذا كان السبب أن اسم الحاوية تغيّر أو أن الخدمات ليست على نفس Docker network، أصلح إعداد الشبكة أو اسم الخدمة في Compose فقط بعد التحقق من المشروع الصحيح.
- إذا كان السبب Restart loop، أوقف إعادة التشغيل مؤقتًا للخدمة المتضررة فقط أثناء التشخيص، ثم أعد تفعيلها بعد الإصلاح.
- شغّل PostgreSQL أولًا وانتظر حتى تصبح healthy أو جاهزة لقبول الاتصالات.
- بعد ذلك شغّل الخدمات التابعة تدريجيًا: auth ثم realtime ثم pooler، وتحقق من Logs كل خدمة.
- إذا وجدت عمليات Zombie ناتجة عن تطبيق Node، حدّد الحاوية أو الخدمة المالكة لها وأصلح آلية تشغيلها أو signal handling بدل قتل عمليات عشوائية.

## التحقق النهائي
بعد الإصلاح، اعرض ملخصًا بدون أسرار يتضمن:
- حالة حاوية PostgreSQL.
- حالة auth وrealtime وpooler.
- عدم وجود Restart loop.
- عدد عمليات Zombie قبل وبعد.
- CPU وload average بعد مرور دقيقة.
- هل المنافذ الأساسية تستجيب محليًا.
- أي خطوة ما زالت تحتاج تدخلًا يدويًا.

ابدأ بالتشخيص فقط، ولا تطبق تغييرات مدمرة أو غير قابلة للتراجع. إذا احتجت تعديلًا، اشرح لي الأمر المحدد وتأثيره قبل تنفيذه.
